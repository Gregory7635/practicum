# Правила для AI-ассистента

Этот документ читает AI-ассистент (Copilot, Claude, Cursor и т.п.) перед тем,
как вносить изменения в проект `delivery-review-analysis`. Правила обязательны.

## Контекст проекта

Сервис принимает отзыв клиента о доставке заказа и с помощью LLM выделяет
проблемные точки (задержка, повреждение упаковки, поведение курьера,
неверный адрес, утеря груза). Используется паттерн **AI Gateway**:
бизнес-логика никогда не обращается к конкретному провайдеру LLM напрямую.

Слои: `controller → service → llm (AiGateway) → client`.

## Разрешено

- Создавать DTO только в пакете `dto` (Java record, без бизнес-логики внутри).
- Добавлять бизнес-логику (построение промпта, парсинг ответа, валидацию)
  только в пакете `service`.
- Вызывать внешние HTTP API только из пакета `client` (например,
  `OpenAiApiClient`), и только через `RestTemplate`/`WebClient`, настроенный
  в `config` с явным timeout.
- Добавлять новые реализации `LlmClient` в пакет `llm` при добавлении нового
  провайдера модели.
- Писать unit-тесты для `service`-layer с моком `AiGateway` (Mockito), для `AiGateway` —
  с моками `LlmClient`, для `client`-layer — с `MockRestServiceServer`; интеграционные
  тесты (`@SpringBootTest`) — с заглушкой провайдера или `@MockBean` на HTTP-клиент.
- Преобразовывать исключения в HTTP-ответы только в `GlobalExceptionHandler`
  (пакет `controller`), формат ошибки — `ErrorResponseDto`.
- Обновлять `application.yml`, если новое поле конфигурации ссылается на
  переменную окружения (`${VAR_NAME}`), а не на литеральное значение секрета.
- Обновлять OpenAPI/описание REST-контракта при изменении `Controller`.

## Запрещено

- Хранить реальные секреты (`api-key`, пароли, токены) в `application.yml`,
  коде или тестах в виде литералов. Только `${ENV_VAR}`
  (в тестах допустимы лишь заведомо фейковые значения вроде `fake-key-for-tests`).
- Вызывать внешние сервисы (OpenAI, любой LLM) напрямую из `Controller`
  или из `service`, минуя `AiGateway`.
- Менять сигнатуру публичного REST API (`DeliveryReviewController`) без
  соответствующего обновления документации/контракта.
- Смешивать JPA entity (если появятся) и DTO — не возвращать entity из
  контроллера, не использовать DTO как объект персистентности.
- Удалять или отключать тесты ради того, чтобы сборка прошла.
- Логировать текст отзыва клиента и сырой ответ модели целиком
  (могут содержать персональные данные) — логировать только факт
  вызова, провайдера и статус.
- Возвращать пользователю необработанное исключение LLM-провайдера —
  всегда должен быть fallback через `AiGateway`.
- Доверять ответу модели без проверки: любой ответ LLM парсится и нормализуется
  в `service` (невалидный JSON, значения вне enum из `domain`).
- Показывать клиенту API стектрейсы и детали исключений.

## Структура пакетов

```
com.logistics.delivery
├── controller   — REST-контроллеры, только HTTP-маппинг
├── service      — бизнес-логика, построение промпта, парсинг ответа
├── client       — низкоуровневые HTTP-клиенты к внешним API
├── llm          — LlmClient, реализации, AiGateway, LlmRequest/LlmResponse
├── dto          — контракты запросов/ответов (record)
├── domain       — внутренние доменные модели
└── config       — конфигурационные классы, LlmProperties
```

## Как добавить нового LLM-провайдера

1. Реализовать `LlmClient` в пакете `llm`, задать уникальный `providerName()`.
2. При необходимости внешних вызовов — добавить HTTP-клиент в `client`.
3. Добавить секцию в `application.yml` под `llm.providers.<name>`.
4. Переключение — правка `llm.active-provider`, без изменений в `service`.
   Резервный провайдер при сбое — `llm.fallback-provider` (необязательно).
5. Добавить тест для нового провайдера и убедиться, что `mvn verify` проходит.
